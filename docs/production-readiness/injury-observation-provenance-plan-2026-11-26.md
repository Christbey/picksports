# Required injury observation provenance adapter

The current read repair deliberately reports unknown observation freshness for legacy injury projections. It does **not** implement verified 48-hour freshness. `source_updated_at` and a local database mutation are different from a successful provider observation, and a verified observation of some rows is different from complete team/feed coverage.

## Confirmed producer mismatch

`AbstractSyncPlayerInjuries::normalizeDateTime` parses the provider timestamp and stores its wall-clock string without conversion to the application timezone. `snapshotSourceUpdatedAt` explicitly converts to the application timezone. The mutable projection therefore cannot establish its original UTC instant merely by parsing the legacy SQL field in the application timezone. A date-only injury onset is also not an exact provider update instant. No historical timezone inference, row rewrite or backfill is authorized by this read repair.

## Concrete next implementation

1. Inventory each of the seven actual injury producers, snapshot implementations and managed provider-refresh receipt kinds. Record which complete source scope they attest (sport, team, feed/request identity and resolved owned players). A successful HTTP response or a recently edited row alone cannot attest complete coverage.
2. Add a versioned future observation envelope/typed projection link: UTC observation epoch (and exact UTC serialization where needed), immutable receipt ID, receipt/source hash, current sport/team/player/injury identity, normalized business-content digest and completeness/partial outcome. Distinguish `provider_observed_at` from optional `provider_status_changed_at`. Missing/naive/date-only provider status-change clocks remain null; a successful qualified observation may still be recent when the underlying status has not changed.
3. Reuse existing immutable injury snapshots or managed refresh receipts only after verifying their current identity, scope, accepted outcome and projection-content binding. Do not promote old mutable rows by copying a latest receipt or inferring a marker from a matching timestamp. Where current receipts lack those guarantees, extend the producer receipt contract first. New sidecars/columns and constraints require additive migration and SQLite/native MySQL proofs; no schema was added in this slice.
4. Ingestion should stage and validate outside SQL, then under the existing current team/game/provider ownership and connection fences atomically persist the projection plus qualified observation binding. Preserve partial-feed rules, ambiguous-player refusal, zero-row complete observations, rollback and prior-history retention. The observation marker must not be renewed by unrelated local edits or old receipt replay. No provider calls under SQL locks.
5. Read freshness only from the qualified bound observation epoch: the configured 48-hour threshold applies to an actual verified observation. A filtered team must not inherit another team's recency. For aggregate boards, expose counts of verified current/stale/unknown rows and explicit incomplete scope; one fresh row cannot hide stale or unknown included rows. Verified empty coverage requires a current complete receipt for the requested scope, not merely zero matching database rows.
6. Preserve the current unknown-safe legacy reader regardless future activation flags. Deploy compatible readers/fences before qualified writers; no old runtime should reinterpret a marker or fall back to a naive clock. Any activation must be based on fake/scoped/native evidence and operator acceptance, without provider refreshes or historical relabeling as a side effect.

## Acceptance

Meaningful tests must cover unchanged-status fresh observations, missing/provider date-only clocks, real source offsets, both DST fold occurrences/session zones, unrelated local edits, stale and fresh teams in one response, filtered scopes, partial feeds, empty-but-complete versus unknown-empty coverage, corrected identity/content, stale/replayed receipts, split connections, claim/commit races and transaction rollback. Existing stored status and detail fields must remain available with honest provenance. No calibration, injury weight retuning, automatic messages, provider calls or old evidence mutation is implied.
