# Relationship ownership and retention review

This domain matrix applies to every model and each association in the [model inventory](relationship-inventory.md). The JSON inventory records each model’s assigned domain, per-relation keys, schema nullability/index/delete policy, inverse candidates and source method. Concrete source import candidates supplement the ownership rules below; shared/inherited consumers are covered by their domain policy rather than pretending every import is a write.

## Constraint and cardinality dispositions

- All application model tables and declared local/owner key columns are checked against a migrated disposable SQLite schema. Package relations exposed through application traits are included; OAuthUser::clients was corrected to the current Passport owner schema.
- Native lineage parents use restricted deletion; optional model/artifact/manifest links retain existing null-on-delete policy and snapshot lineage metadata. Canonical event-to-prediction cascade is retained for imported derived rows; native runs/input snapshots/results/evaluations restrict deletion of their event and revision parents. No blanket cascade rewrite was introduced.
- Player/Team current membership inverses remain separate from observation team_id. No hasManyThrough is used for home-or-away membership. The six Team forecast builders are explicitly named queryPredictions.
- Latest CFB live snapshot and latest canonical evaluation are declared one-of-many selections, not missing uniqueness. MLB starting pitcher selectors use side plus forecasted_at/ID ofMany. WCBB tracked spread is one per forecast under the recorder’s unique deterministic decision_hash policy; historical decision collections remain many.
- Group join-link ownership was intended one-to-one but its old chained unique call did not create the index. The additive forward migration explicitly creates uniqueness, refuses duplicate groups without deleting links, and is tested on the disposable schema.
- Legacy generic PlayerProp remains provider-keyed compatibility storage with four explicitly supported sports. Both its player resolver and newly guarded gameable relation refuse unsupported mappings. UserBet morphs are allowlisted and validate sport/event identity; no global morph-map conversion is required.
- Missing useful ownership belongsTo methods were added for CFB GameDataCheck.game, NFL GameContextFact.game/team and NFL ResearchDocument.source. Other absent inverse methods are retained when no owning query needs them; symmetry alone is not a reason to add methods.
- Table/ID odds, live, decision, feature and evaluation references remain explicit typed record references, not falsely declared ordinary FKs. SportRecordResolver covers game/table, legacy/canonical prediction/table, public prediction IDs, provider event identities, canonical detail ancestry and allowlisted alert/delivery classes. Publication/release approval remains the reader’s responsibility.

## Audit environment and limits

The schema/integrity artifacts describe all repository migrations applied to a new, disposable SQLite :memory: database. That baseline has zero application data rows. Read-only counts return zero orphans/duplicate groups/identity mismatches there; separate seeded tests deliberately create invalid data and verify those counters and safe migration rejection. This is local schema/behavior validation, not a production record audit.

No production records were read, repaired, merged, deleted or backfilled. If the forward migration encounters existing duplicate join links in a deployment, it stops and requires explicit data review. MySQL deployment migration execution remains a release-time check; no deployed schema status is claimed.

## Retained roster writer policy

Legacy basketball boxscore ingestion still updates the mutable Player.team_id from the imported athlete/team identity. This is retained source-compatible behavior under C06, including when historical boxscores are imported. C45 does not redesign the current-roster writer or claim that a historical backfill cannot change current roster membership. Its guarantee is that historical readers use recorded stat.team_id, game identity and frozen snapshots rather than deriving historical ownership from the mutable Player.team relation. Any separate point-in-time roster writer policy needs an explicit follow-up and numerical/input review.
