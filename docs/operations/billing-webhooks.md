# Billing and Stripe webhook admission

The application-owned `POST /stripe/webhook` route always requires Stripe signature verification. A missing or blank `STRIPE_WEBHOOK_SECRET` returns 503 before billing events are dispatched. Invalid, missing or expired signatures return 403. Verification uses Cashier's installed Stripe verifier and configured tolerance against the original request bytes.

Only this webhook path is exempt from browser CSRF checks because Stripe authenticates through its signature. Browser subscription checkout, cancellation, resumption and portal actions retain web authentication and CSRF protection. Do not disable signatures to troubleshoot delivery. Configure the correct endpoint signing secret through the deployment secret store; never copy it into documentation, source or logs.

Subscription management redirects accounts without a subscription to plans. Inactive database tiers cannot be purchased through an old configured tier/price fallback. Existing subscriber entitlement is a separate policy: retiring a tier from sale does not automatically terminate a paid subscription.

Local tests use synthetic signed requests and mocks, with CSRF protection explicitly enabled. They do not establish live Stripe delivery, account mode, price/product ownership, billing portal configuration, webhook replay/order handling or reconciliation. Before release, verify the exact configured endpoint and secret privately, then exercise a test-mode subscription lifecycle without real customer charges. Provider event ordering, duplicate deliveries and durable reconciliation still require a separate recovery implementation. Known-customer subscription created/updated/deleted handlers now pair vendor database writes and role synchronization in one transaction after connection/identity checks and a user-row lock. Other inherited handlers are outside that scoped guarantee.

The implementation uses the vendor Cashier route/controller behavior for subscription updates. For the three supported subscription event types, access-role synchronization is part of the same local transaction. Non-trial cancellation period retrieval happens before that transaction, with a local subscription/item snapshot checked again under lock; changed state rejects for retry. Trial cancellation copies use the prepared local end too, so expiry while acquiring locks cannot trigger a provider lookup under the transaction. Unknown local customers still follow Cashier acknowledgement behavior. No durable inbox, external idempotency ledger or event-order guarantee was introduced in this pass. See [the bounded recovery design](../contracts/billing-recovery-design.md) for remaining gates and timestamp compatibility limits.

Supported subscription handlers require a standalone database lifecycle: direct calls inside an inherited transaction are refused before customer/provider lookups. Their SQL transaction uses current locking reads for the subscription/item drift check. This bounds the vendor ordinary-read behavior to a fresh webhook transaction rather than claiming safety inside arbitrary older repeatable-read snapshots.
